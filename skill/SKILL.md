## Описание навыка

Навык реализует **полный конвейер разведки** компании

### Список собираемых данных

* **Контакты**: телефон, e‑mail, соц‑сети, сотрудники с должностями; если прямых контактов нет – любые значимые контакты с указанием ссылки.
* **Сфера деятельности** компании (ОКВЭД, описание продукции/услуг).
* **Новости компании** за последние **3 года**.
* **Вакансии**: должность, город, дата размещения.
* **Прямые потребности** компании (запросы, задачи, проблемы) – даже если они не соответствуют нашему профилю.
* **Связанные контакты и компании** с описанием их отношения к организации или её сотрудникам.

> Если в конкретной задаче условия иные, приоритет условиям и инструкциям из этой задачи.

### Цели разведки

* Поиск потенциального клиента для отдела продаж.
* Изучение потребностей компании в услугах вашей организации (профиль компании — configs/company\_profile.md).

## Процесс разведки (по шагам)

1. **Создать папку задания** – название `<YYMMDD>\_<Название компании>\_<ИНН>` в каталоге `{BASE\_DIR}`.
2. **Поисковые системы** – по умолчанию DDGS; при необходимости переключиться на Google через `googleparser` (прокси `127.0.0.1:7891`, не чаще 1 раз в 10 мин). Yandex XML доступен только при наличии переменных `YANDEX\_USER`/`YANDEX\_KEY`.
**Поиск по компании — строго в 2 прохода:**

   1. **Проход 1:** поиск по названию компании **без организационно-правовой формы** (не «АО Пример», а «Пример Город»). ООП-формы (АО, ООО, ОАО, ПАО, ЗАО) в запросе засоряют выдачу агрегаторами и сужают результаты.
   2. **Проход 2:** поиск по ИНН — только после того, как ИНН найден в проходе 1 (например, со страницы «Контакты» официального сайта). Поиск «<название> ИНН <номер>» подтверждает реквизиты и вытягивает оставшиеся источники.
Если в задаче ИНН дан изначально — проход 1 всё равно выполняется первым (по названию), проход 2 — уточнение по ИНН.
3. **Отфильтровать сниппеты** – убрать явно нерелевантные результаты, классифицировать по типу (ЕИС, list‑org, hh.ru и др.).
**Пагинация новостей сайта — проверять на «та же страница»:** при обходе `?page=N`/`?PAGEN\_1=N` сравнивать дату/заголовок первого поста текущей страницы с предыдущей; если совпали — пагинация не работает (JS-навигация), остановиться сразу, не тратить вызовы. Проверено на stc-spb.ru (2026-09-03: `?page=2` и `?PAGEN\_1=2` отдают страницу 1; архив гостю недоступен — берём только первую страницу).
**Фильтрация агрегаторов на уровне парсера:** `parsers/search\_all.py` содержит `DOMAIN\_BLACKLIST` — чёрный список доменов-агрегаторов (rusprofile, СПАРК, audit-it, checko, Контур.Фокус, zachestnyibiznes, РБК Компании, СИНАПС, saby, cbonds, Скрин, Картотека, vbr, tbank, 1prime, star-pro, b2b.house, sudact и др., включая list-org.com — он обрабатывается отдельным шагом процесса). Они отсекаются до вывода; в JSON возвращаются поля `total\_raw`, `total\_filtered`, `dropped\_domains`. Запрашивать **3 страницы** (`max\_pages=3`) — на 2 страницах теряется часть результатов. При TimeoutException/RequestError одного бэкенда парсер сам ретраит по цепочке auto→duckduckgo→google→yahoo (region ru-ru, 2026-09-08; bing в text-бэкендах DDGS отсутствует) — падение всего прогона исключено. **Токен-экономия (2026-09-08):** stdout — компактный JSON: stats (raw/filtered/dropped-счётчик) вместо списка dropped\_urls; при `--fetch` тело страницы чистится (script/style/nav/footer прочь, дедуп строк, wayback-шум вырезан) и режется до 12000 симв.
**Закупки/ЕИС:** для тендеров использовать `parsers/zakupki\_223\_parser.py <ИНН> \[max\_pages]` (работает напрямую с zakupki.gov.ru: карточка заказчика 223-ФЗ, договоры, план закупок — по ИНН, без браузера). **Фильтр заказчика (2026-09-09):** записи реестра с customer != искомой организации отбрасываются (extendedsearch/реестр по customerIdOrg может отдавать чужие закупки); счётчик отброшенных — `customer\_filtered` в JSON. **Извещения (extendedsearch) по customerIdOrg не работают для заказчиков без активных процедур — пусто в JSON это норма, не сбой (вынесено из вывода парсера в SKILL.md 2026-09-09). Пагинация: по умолчанию max\_pages=5 (до 100 записей на секцию); для гигантов с тысячами договоров поднимать аргументом (РЖД: 5 страниц = 50 договоров, 10 страниц = 100).** Активные извещения — extendedsearch (пусто, если процедур нет); исторические данные — реестр договоров `/epz/contractfz223/`. SSL ЕИС: verify=False только для этого домена.
**Закупки/коммерческие (tochka.com):** `parsers/zakupki\_tochka\_parser.py <ИНН>` — парсит страницу заказчика `zakupki.tochka.com/customers/<ИНН>/`. Сайт Next.js SSR: список закупок лежит в потоке `self.\_\_next\_f.push(\[1,"..."])` как JSON-объекты `{"purchase":{...}}` (seldonId, subject, purchasePrice, status, endDate, notificationNumber, purchaseLink — прямая ссылка на ЭТП заказчика). Извлечение — балансным проходом по скобкам. Пагинация `?page=N` до первой пустой. Дедупликация с ЕИС по номеру извещения; в tender.csv для вторых ссылок — колонка «Ссылка на тендер 2».
4. **Собрать информацию по ссылкам**:

   * Сфера деятельности (ОКВЭД, описание).
   * **Компании-заказчики (холдинги, закупочные центры, застройщики) — искать TAdviser-профиль** (`site:tadviser.ru <название>` или прямой запрос): масштаб, собственники, топ-менеджмент, выручка холдинга — всё в одном запросе (проверено на крупном заказчике: масштаб холдинга, собственники, выручка — в одном запросе). Решение пользователя 2026-09-07.
   * Полные контакты и ссылки.
   * Новости (≤ 3 года).
   * Вакансии (должность, город, дата).
   * Прямые запросы/потребности.
   * Государственная поддержка, субсидии.
   * Тендеры из ЕИС и b2b‑center → `tender.csv`.
   * Данные из **list‑org.com** (контакты, ОКВЭД, выручка, лицензии, господдержка, динамика за 5 лет).
   * Связанные компании/контакты и их отношения.
5. **Проверка доменов и поддоменов** – собрать в `domain\_count.txt` (файл хранится вне проекта).
**Парсер:** `parsers/domain\_probe.py <domain1> \[domain2 ...] \[--json|--llm]`. **Альтернативные TLD (2026-09-09): флаг `--tld-alts` — к каждому домену автоматически добавляется проверка <имя>.ru↔<имя>.com одним вызовом** (второй официальный домен мог быть найден только отдельным DDGS-запросом — теперь проверяется сразу). В конвейере: найден официальный домен → сразу `domain\_probe.py <домен> --tld-alts`. Два режима (2026-09-08): по умолчанию **LLM-компактный JSON** (domain/dns/tls/site/subdomains/wayback, без len/server/indent, пустые поля отброшены, \~40-60% меньше); `--json` — полный технический (включая external\_domains). Оптимизации: DNS одним dig-вызовом (+noall +answer, A/AAAA/MX/TXT/NS), поддомены — минимальный probe (status/title) параллельно (ThreadPool), wayback только если типовых поддоменов найдено <3, 404/mojibake-поддомены отбрасываются. Ссылки на внешние домены (поставщики/партнёры) — помечать как связанные, не как собственные; domain\_probe по ним НЕ запускать (решение 2026-09-03).
6. **Собрать данные с официального сайта** – дополнить MD‑карточку (например, /contacts/, /vakansii/, /partneri/, /news/).
\*\*Страницы для поставщиков — обязательный поиск : на сайте компании искать разделы/страницы для поставщиков и партнёров — «Партнерам», «Поставщикам», «Закупки», «Потребности», «Сотрудничество», «Тендеры» — как в русской транслитерации URL (/partneri/, /postavwikam/, /zakupki/), так и в английской (/partners/, /suppliers/, /purchases/, /procurement/, /tenders/, /cooperation/). Такие страницы содержат прямые контакты закупочных служб и формы «стать поставщиком» — для вашей компании это главный вход. Ссылки на них часто спрятаны НЕ в меню, а на странице «Контакты» (подразделы «Закупки», «Отдел закупок» с телефоном/e-mail) и в футере сайта. **При проверке страницы «Контакты» внимательно проходить весь текст: телефоны/почты закупок, ссылки на закупочные порталы и регламенты — фиксировать отдельным блоком в карточке.** Если раздел не найден явно — серия DDGS-запросов `site:<домен> <ключевое слово>` ПО ОТДЕЛЬНОСТИ (закупки, поставщикам, партнерам, тендеры, purchases, suppliers, procurement) перед выводом «раздела нет». ВАЖНО: OR-синтаксис в DDGS не работает (`a OR b` возвращает мусор или склеивает выдачу некорректно — проверено на filetype-серии 2026-09-08) — только одиночные запросы по одному ключевому слову.
**Универсальное правило (2026-09-08, распространено с Tilda на все сайты): меню главной страницы = карта реальных URL. Сначала парсить главное меню ИЗ HTML главной (ссылки `<a href="/...">`), фетчить ТОЛЬКО целевые интересующие разделы (контакты, о компании, продукция, вакансии, новости, страницы для поставщиков — см. выше) — не гадать по 404-шаблонам.** Кейсы: (а) Tilda (`tilda-` классы, `tildacdn`) — навигация JS, типовые /contacts/ отдают 404-шаблон; (б) самописные CMS без SSL-редиректа на поддоменах (nzta.ru) — каталог перебирать не нужно, структура меню видна из главной; (в) любые старые сайты — то же самое.
7. **Парсинг соцсетей** (ВКонтакте, TenChat, Сетка) – максимум 2 года, ≤ 100 постов, ≤ 20000 символов, собрать подписчиков, сотрудников, ссылки на посты.
**ВКонтакте:** сайт закрыт login-wall (html отдаёт пустой SPA-скелет и desktop, и m.vk.com); VK API без токена возвращает «Access denied: token required». Использовать `parsers/vk\_group\_parser.py` (groups.getById + wall.get: описание группы, контакты сообщества, посты ≤2 лет / ≤100 шт. / ≤20000 симв. со ссылками). **Вызов ТОЛЬКО при найденном сообществе (решение пользователя 2026-09-09): если официального сообщества нет в поисковой выдаче — парсер вхолостую не дёргать, негатив «официального сообщества ВК нет» фиксировать в карточке вручную; парсер — для проверки конкретного найденного алиаса/ID (валидация имени отсечёт случайные группы).** Токен: `VK\_SERVICE\_TOKEN` в окружении или `/Hermes/.env.vk` (сервисный ключ, https://dev.vk.com/ru/api/access-token/getting-started). **Ограничение сервисного ключа:** users.search недоступен («method is unavailable with service token») — поиск сотрудников по подписчикам требует пользовательского токена с правами. Без токена — фиксироваться только URL сообществ и публичное описание (через поисковые сниппеты).
**Поиск сотрудников ВК (шаг «Профили вероятных сотрудников ВК» — обязателен в любом проходе, даже без официального сообщества): ТОЛЬКО шаблоны для ручной проверки в браузере, парсинг сотрудников ВК запрещён решением пользователя.** Формат в карточке — URL-кодировка (кириллица/пробелы в процент-энкоде, чтобы ссылки были кликабельны) + рядом краткая расшифровка поискового запроса: `1. \[https://vk.ru/search/people?city\_id=2\&company=%D0%92%D0%90%D0%94](...) — «ВАД», СПб`. Варианты: (1) `https://vk.ru/search/people?city\_id=<ID>\&company=<название кириллицей, URL-энкод>`; (2) `...?company=<название без ОПФ, URL-энкод>`; (3) `...?company=<название латиницей>`; (4) `...?company=<ОПФ> <название>, URL-энкод`. city\_id: Москва=1, СПб=2, Волгоград=10, Владивосток=37, Воронеж=42, Екатеринбург=49, Казань=60, Калининград=61, Краснодар=72, Красноярск=73, Нижний Новгород=95, Новосибирск=99, Омск=104, Пермь=110, Ростов-на-Дону=119, Самара=123, Уфа=151, Хабаровск=153, Челябинск=158, Севастополь=185, Симферополь=627; прочие города — VK API database.getCities (сервисный токен). Веб-поиск требует залогиненной сессии; users.search недоступен с сервисным токеном.
**TenChat (шаг обязателен, проверено 2026-09-02 на тестовых прогонах):** страница `https://tenchat.ru/<ОГРН только цифры>` отдаёт Nuxt-payload (`\_\_NUXT\_DATA\_\_`) с сотрудниками компании (объекты с полями name/surname/username/position/city/birthDate/workStatus, а также ЕГРЮЛ-блок: ИНН/ФИО директора, доля, дата). Парсинг: `json.loads` payload, фильтр dict'ов с ключами name+surname/position, значения-индексы резолвить из того же массива. Страница поиска `tenchat.ru/search/people?ogrns=<ОГРН>` гостю результатов НЕ отдаёт (payload пуст) — проверять именно страницу компании. Дополнительно: `site:tenchat.ru <название>` в DDGS находит username-профили (напр. tenchat.ru/company\_name).
**Парсер с кешем:** `parsers/tenchat\_parser.py <ОГРН> \[--refresh]` — кеш 30 дней в `{BASE\_DIR}/.tenchat\_cache/<ОГРН>.json`. ВАЖНО: в Nuxt-payload значения-индексы — простые int в общий массив (НЕ `\['Ref', N]`).
**Сотрудники (решение 2026-09-09):** парсер тянет `/<ОГРН>/employees` и отдаёт массив `employees` — ФИО, должность (position резолвится через dict{name}) и **ссылку на профиль каждого** (`https://tenchat.ru/<username>`). Этот список идёт в раздел «Контакты» КАРТОЧКИ — построчно: ФИО — должность — ссылка на профиль (решение пользователя 2026-09-09: нельзя просто ФИО и общую ссылку на компанию). Гостю TenChat отдаёт только видимых сотрудников (2-5) — если employeeCount >> видимых, фиксировать «список усечён гостем». position=None — допустимо (должность не указана).
**Telegram-каналы:** `parsers/tgstat\_parser.py <username>`. Источники по приоритету: telegram-dialogs.ru/channel/@user (ОТКРЫТ гостю: подписчики + 3 последних поста с датами/просмотрами) → DDGS-сниппеты tgstat.ru → Wayback CDX. tgstat.ru/com под Cloudflare (403 гостю и ботовым UA); t.me на хостинге TCP-блок (149.154.167.99 не маршрутизируется, sing-box тоже TLS-reset).
8. **Собрать вакансии с hh.ru** – при наличии указать контактных лиц.
**Парсер:** `parsers/hh\_vacancies.py <employer\_id> \[max\_pages]`. Схема: api.hh.ru отдаёт 403 для всех UA без зарегистрированного приложения («bad\_user\_agent»/«forbidden») — использовать веб-поиск `hh.ru/search/vacancy?employer\_id=<ID>\&area=113\&page=N` (SSR HTML). Выдача (2026-09-08, BS4-каркас): контейнер `div.vacancy-card--<hash>` → title по `data-qa="serp-item\_\_title-text"`, зарплата — текстом в карточке («85 000 – 101 000 ₽»; data-qa compensation в SSR пуст), город — `data-qa="vacancy-serp\_\_vacancy-address"`. Ретрай 429/5xx (2 повтора, 10/20 с), пауза между страницами random 5–7.5 с, stdout только JSON (диагностика в stderr), `parser\_status`/`stop\_reason`/`warnings` в выводе; prod-вакансии считаются по ключевым словам (токарь/слесарь/ЧПУ/сварщик...) — гигант с <2 prod-вакансий в выборке помечается partial. Ограничения: 20 вакансий на страницу, гостю отдаётся глубина 2 страницы (40 шт.) даже если счётчик больше; **гиганты (счётчик ≥6000 вакансий, 2026-09-08): парсер сам режет до 2 страниц (giant\_limit\_applied в JSON) — производственный профиль виден и так;** пауза ≥5 сек между запросами (иначе пустой ответ); гео-подмена выдачи (региональный домен lipetsk.hh.ru и пр.) — парсить по маске `/vacancy/<id>`; город и дата публикации в SSR не отрисовываются (JS) — город брать из карточки, дата = дата прохода. Employer-ID искать по ссылке «vacancies на hh» на сайте компании или через DDGS `site:hh.ru <название>`.
8b. **Файловый поиск DDGS (обязательный шаг, решение 2026-09-08 — ранее выполнялся нерегулярно):** после базового поиска по компании выполнить серию через `parsers/search\_all.py`:

   * `<имя компании>` (уже сделано в п.5);
   * `<имя> <ИНН>`;
   * `<имя> <ИНН> filetype:xls`;
   * `<имя> <ИНН> filetype:xlsx`;
   * `<имя> <ИНН> filetype:pdf`.
ВАЖНО (проверено 2026-09-08): OR-синтаксис `filetype:xls OR filetype:xlsx` в DDGS НЕ объединяет
результаты — он возвращает мусор из нерелевантных сайтов. Только одиночные filetype-запросы.
Читай СНИППЕТЫ (названия файлов, упоминания контактов/сотрудников/потребностей/цен), по ним решай, качать ли файл. В xls/pdf: контакты сотрудников, потребности, прайсы, реестры закупок. Файлы качать выборочно. **Результат серии фиксировать в recomendations.txt** (какие запросы дали результаты; filetype:xls пуст — это тоже факт, не пропуская). Если серия не выполнена — это нарушение процесса, отметить в «Технических замечаниях».

Служебные блоки (`\_meta`, `\_sources\_checko`, `fallback\_\*`) приходят ОДНОСТРОКОЙ (JSON-в-строке) — для программного доступа `json.loads`; агенту читать глазами ок. ## Свежая отчётность ПАО (когда Checko отдаёт устаревшую)

Checko для ростеховских ПАО часто отдаёт отчётность 5-8-летней давности. Порядок получения свежей:

1. **Раздел «Акционерам и инвесторам» на сайте компании** — первичный источник: годовые отчёты, отчёты об итогах голосования ОСА, бюллетени СД в PDF (напр. ПАО: годовые отчёты в PDF в разделе «Отчётность»). PDF читаются pypdf.
2. **e-disclosure.ru** — под анти-ботом (JS-challenge, requests не проходит; curl — Forbidden). ID компании можно взять из сообщений на зеркале **disclosure.ru** (страницы сообщений `/rus/corpnews/news.shtml?newsisn=<N>` содержат пункт 1.6 «Адрес страницы в сети Интернет... e-disclosure.ru/portal/company.aspx?id=<ID>» и уникальный код эмитента Банка России). Страница эмитента на disclosure.ru: `/issuer/<ИНН>/` (может быть деактивирована — тогда только сообщения через DDGS `site:disclosure.ru <название>`).
3. Если и это не даёт цифр — фиксировать «свежая отчётность ПАО утверждена (дата ОСА), но не опубликована в открытом доступе» — сам факт годового собрания уже событие для карточки.
Проверено на ПАО оборонного сектора (2026-09-03: Checko 2018 → PDF-отчёт ОСА актуального года с сайта).

## Обработка ошибок

* При любой ошибке записывать в `{BASE\_DIR}/parsers/debug.log` строку:

```
\[<timestamp>] ERROR <step> – <детальное описание: запрос, код ответа, исключение>
```

* При каждом проходе писать краткое резюме в `recomendations.txt`:

  * **Сложности** (например, блокировка Google, отсутствие API‑ключей, ограничения Яндекса).
  * **Возможные улучшения** (кеширование, оптимизация запросов, увеличение количества запросов за раз).
  * **Оценка токен‑экономии** (рекомендации по сокращению количества запросов/размеров ответов).
* **Статус каждой рекомендации обязателен.** Каждая строка в разделах «Возможные улучшения» и «Рекомендации» помечается явно:

  * «ИСПРАВЛЕНО: <что>» — если исправление уже внесено (в парсер, SKILL.md, кеш и т.п.; указать где);
  * «РЕКОМЕНДУЕТСЯ ИСПРАВИТЬ: <что>» — если исправление только предлагается и ничего ещё не тронуто.
Не допускаются формулировки без статуса («можно улучшить», «стоит добавить») — по ним невозможно понять, сделано ли уже. Запись в recomendations.txt — не отчёт о желаниях, а реестр изменений/предложений.

## Источник EUR-Lex (компании под санкциями ЕС)

Если в выдаче поисковиков по ИНН появляются сниппеты `eur-lex.europa.eu` (регистрационный номер = ИНН, «... JSC holds two licenses...», «a.k.a. ...») — компания в санкционных списках ЕС. Прямой запрос по сайту EUR-Lex по ИНН даёт список и упоминание лицензий Минпромторга, работает без прокси. Факт записывать в карточку (раздел «Сфера деятельности» или отдельной строкой) с пометкой о необходимости комплаенс-проверки при сделках с иностранным компонентом.

## Требования к окружению

* Python 3.11+, `python3` в PATH.
* `ddgs` установлен (скрипт устанавливает при отсутствии).
* `googleparser` – `pip install --quiet googleparser`.
* Прокси SOCKS5 `127.0.0.1:7891` обязателен для всех HTTP‑запросов, кроме DDGS.
* Переменные окружения:

  * `YANDEX\_USER` / `YANDEX\_KEY` – только для Yandex XML.
  * `SERPAPI\_KEY` **не требуется** (используется googleparser).
* Ограничение частоты запросов к Google: файл `{BASE\_DIR}/.google\_last\_ts` хранит время последнего запроса; если прошло <600 сек, скрипт ждёт оставшееся время.
